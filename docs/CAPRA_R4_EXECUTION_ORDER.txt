## 5. 运行前的正确性和不变性检查

1. **数据正确性**：原80个作业逐一匹配，只允许 `time` 按公式变化；名称与字段稳定；Original/CM 均共享同一派生 trace。
2. **R3 默认行为不变**：在冻结的 R3 少量调度状态上，R4 接入前后的 GPU plan、batch、节点布局、CPU/RAM 配额、恢复锁、费用、Phi、选中候选和训练进度应一致（除新增只读诊断元数据、计时和文件路径）；失败就不要启动正式矩阵。
3. **smart 独立性**：其 MIP 调用次数和原 smart 适配规则保持；比例资源没有使用 preferred/NodeAllocator/ram_slack；smart 非法输出不能静默改成 FK 或 fast。
4. **FK 不计算 R**：对执行路径和计时组件作断言。FKR 可行候选中始终保留 F/K 作为参照，并在失败时安全回退。
5. **资源/执行审计**：逐节点 GPU、CPU、RAM 不超额，作业完整且不重复；恢复锁与真实迁移收费一致；画像倍率只生效一次；JCT 时间账本守恒；当前统计的 GPU 使用积分含恢复，不得当作 busy utilization。

## 6. 核心机制：R 机会漏斗，不能只看 R 选中次数

对全部 12 格，特别是 FK/FKR，在真实的同轮 GPU 分配、节点状态、锁与辅助资源画像下生成可追溯的机会漏斗。尽量从现有事件日志只读计算，不能为了得到漏斗修改算法的动作。R3 的 `analysis/metrics.json` 的指标是起点，但不少计数会重叠；本轮应同时提供**同一分母下的严格嵌套漏斗**和非互斥标签。

建议每轮依次区分：
A. GPU MIP 本轮选出哪些可运行作业及同型节点的剩余容量；
B. 是否有具不同 CPU/RAM 需求、潜在互补的同 GPU 类型作业对；
C. 对应 GPU 数量是否可在目标节点组合中合法容纳；
D. 是否已经在 F/K 中得到适当共置，剩余可改进空间有多大；
E. 是否满足恢复锁、最低 CPU/RAM 配额、逐节点容量和完整作业集合约束；
F. R 的有限候选集合能否覆盖这样一个不同的合法布局；
G. 重新用同一节点分配器评分后，候选是否比 F/K 的预测净得分更高；
H. 迁移与恢复成本扣除后，是否实际选中 R；
I. 最终执行的 CPU/RAM 绩效倍率、GPU 配置变化、迁移、等待、训练、恢复及作业 JCT 如何变化。

每个漏斗层级必须说明分母、去重规则和条件逻辑；未进入前一层的轮次不能进入后一层。并行输出非互斥标签和直接证书：已共置、不同 GPU 池、GPU 碎片、当前资源容量不足、恢复锁阻塞、未生成 R 候选、候选预测增益不足/恢复费过高、R 选中但结果退化等。`pair exists` 只是必要线索，不等于资源互补**可获得正净收益**；不能从互相重叠的两个汇总计数相减推断错过的机会数。

对 R2 W2-CM 中的正收益与 R3 Saturn8-CM 中的负收益，使用冻结的已有日志做只读对照，选出可追溯的代表轮次；这只是解释，不重新运行原实验。R4 若有 R 选中后变差的作业，展示真实 `job_id`、轮次、节点/配额变化、预测倍率、预测迁移费、实际训练/恢复时间与随后的 GPU 重新配置。严格注明：**整条动态轨迹会分化，时间账本差不是某单轮行动的严格因果效应。**

如发现存在潜在可行资源组合但 R 没枚举到，只在最多若干个预先抽取的小状态上做离线可行性/局部枚举审查，明确该分析的候选上限，不能把局部枚举结果称为全局 JCT 最优；这属于诊断，不进入正式算法，也不生成额外实验主表。

## 7. 评估指标与数据解释

每格必报：
- submitted、completed、censored、mean/median/P95/P99 JCT、makespan；
- 平均等待、有效训练、恢复及其逐作业分解；
- 分应用 JCT，paired jobs 的快/相同/慢数量及最差相对、绝对退化；
- GPU 每类型、每节点、全局的分配资源时间占容量时间比、并发活跃作业与等待队列时序；明确它不是GPU物理忙碌率；
- CPU/RAM 比例配额之外的实际条件性能增益、训练加权 `rho`、原节点已互补/新重排机会；
- F/K/R 的候选数量、合法性/失败原因、选择次数、预测 Phi 差、实际迁移次数与费用；
- 决策 median/P95/P99/max、超过5秒次数、单轮最坏成本及分组件时间（GPU MIP、identity、allocator、R、审计）；
- 所有资源/状态/账本审计与 input/source/result 哈希。

主对照：每个 dense05/Original或CM下比较：`FK/SMART`、`FKR/SMART`、`FKR/FK`；改善率定义 `100*(1-method/baseline)`，正值表示 JCT 更低。与 R3 相同 trace 的原到达场景进行压力前后比较，但只能作为**场景敏感性**，不能把压力变化算成算法贡献或独立样本。

注意：增密并不必然增加可利用互补机会；更高 GPU 占用可能使 CPU/RAM 更紧缺、R 可行空间更小。若确实没有使GPU压力或有净收益的布局机会增加，应如实判定“该压力构造没有充分激发目标机制”，不得现场改到达率或筛选场景来追求提升。
