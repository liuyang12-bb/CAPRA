## 一、目标与本轮修改范围

回答四个问题：

1. 更高并发能否增加可利用的辅助资源优化机会，还是仅增加同类资源竞争？
2. CPU 容量改变时，比例配额、节点内重分配和自由放置的相对表现怎样？
3. 在不更换原 GPU 训练任务的前提下，让较长任务具备低 CPU 需求，是否能形成更持续的资源互补？
4. 在 CPU 互补场景上，只增加一类任务的 RAM 敏感性，现有算法能否利用新增的 RAM 优化机会？

saturn-2-supported80          1056.1125    971.0250        949.4625
saturn-6-supported80          1056.5500    973.7250        911.4750

对应：

- CAPRA 相对 Fixed 改善约 2.22% / 6.39%。
- W2 的 CAPRA 相对 SIA-P，P95/P99 分别增加约 5.70%/9.37%，须保留这个尾部现象。

- 原画像中 DeepSpeech2 在比例点已达该表最高倍率，继续增配没有收益；BERT 可释放辅助资源，但其实际训练份额较少。

这些用于形成研究问题，不是新实验必须复现的收益目标。v2 已有平均收益，本轮要分清配额、放置、恢复和场景机会的关系。

## 三、固定六个新增场景：共 18 格

每个场景使用同样三种方法，顺序固定：
SIA-P → CAPRA-Fixed → CAPRA。

场景按以下顺序执行：

1. w2_dense_original
   W2 原 80 作业；到达间隔缩短一半；CPU/GPU=3；原响应表。
   问题：只增加并发后，辅助资源优化机会怎样变化？

2. w6_dense_original
   W6 原 80 作业；到达间隔缩短一半；CPU/GPU=3；原响应表。
   问题：在第二份原负载上复核到达密度的影响。

3. w2_dense_cpu2
   与场景 1 完全相同的作业和到达；仅 CPU/GPU 从 3 降为 2；原响应表。
   问题：CPU 更紧缺时，是否还有可回收的冗余资源和有效增配空间？

4. w2_dense_cpu6
   与场景 1 完全相同的作业和到达；仅 CPU/GPU 从 3 增为 6；原响应表。
   问题：CPU 较充裕时，比例分配已经更强，重新分配和放置还剩多少增量？

5. w2_dense_cn
   与场景 1 相同的原 GPU 训练任务、到达、拓扑和费用；使用下面定义的 C/N 辅助响应。
   CIFAR=C 类，DeepSpeech2=N 类，BERT=N 类。
   问题：增加较长时间存在的 CPU 捐出任务，是否形成可持续的 CPU 互补？

6. w2_dense_cm
   与场景 5 完全相同，仅把 DeepSpeech2 的辅助响应从 N 改为 M。
   CIFAR=C 类，DeepSpeech2=M 类，BERT=N 类。
   问题：在完全相同的比例基线下，新增 RAM 敏感性是否产生可利用收益？

这六个场景是有目的的机制覆盖，不是完整因子实验。CPU 容量和合成敏感度部分只使用 W2，结论不要写成已经跨大量负载普遍验证。

更拥挤、CPU 更多或更少都不必然有利于 CAPRA。全部场景一起报告，不能依据胜负增删场景或调整参数。

## 四、精确生成规则

### 4.1 到达密度

对原 CSV 每个作业：

t_new = t_min + (t_old - t_min) / 2。

- 保留首到达时刻、原有行顺序和同时到达关系。
- 保留可能出现的半秒，不四舍五入到整秒。
- 保留全部 80 行，不新增、删除或选择有利子集。
- name、application、num_replicas、batch_size 逐字段保持原值。
- 不更改应用训练终止条件、GPU 性能表或训练量。

核对：
W2 原首/末到达 101 / 20088，压缩后末到达 10094.5。
W6 原首/末到达 22 / 22112，压缩后末到达 11067。

### 4.2 CPU 容量

保留节点 ID、GPU 类型、每节点 GPU 数、RAM 及节点数量：

- aws:0/1：各 4 GPU。
- dgx-ext:0/1、rtx:0/1：各 8 GPU。
- 原 CPU/GPU=3：4 GPU 节点 12 CPU；8 GPU 节点 24 CPU。
- CPU2：改为 8 CPU 和 16 CPU。
- CPU6：改为 24 CPU 和 48 CPU。
- RAM 保持 4 GPU 节点 250 GB、8 GPU 节点 500 GB。

保持 40 GPU、两节点/类型、单作业单节点的 v2 支持域，不增加节点或改变 GPU 结构。

### 4.3 共同性能参考点

原响应参考点始终是每 GPU 的 3 CPU / 62.5 GB，倍率为 1。
容量变化时不重新归一化响应表。

因此，SIA-P 比例配额下：
- CPU2：CIFAR rho=0.72，DeepSpeech2 rho=0.66，BERT rho=1。
- CPU6：CIFAR rho=1.75，DeepSpeech2 rho=1，BERT rho=1。

这是容量变化对三种方法共同产生的影响。不能把 CPU6 下 rho>1 全部记成调度优化收益，也不能因 CPU2 下 rho<1 就认为执行器出错。

性能保底继续相对“本场景实际节点的比例配额”计算。

## 五、C/N 与 C/M 的精确响应表

本节只改变辅助资源响应。原 application 标签、GPU goodput 模型、batch、训练量、到达、GPU 需求、恢复成本全部保留。

沿用原 CPU 轴：
[1, 2, 3, 4, 5, 6, 9, 12, 24]，单位 CPU/GPU。

沿用原 RAM 轴：
[20.83, 62.5, 125, 187.5, 250]，单位 GB/GPU。

### C：CPU 敏感、RAM 平坦

用于 CIFAR。取原 CIFAR 在 RAM/GPU=62.5 处的 CPU 截面：
[0.37, 0.72, 1, 1.3, 1.53, 1.75, 2.4, 2.4, 2.4]。

将每个 CPU 点的值沿全部合法 RAM 点重复。
例如 CPU/GPU=6 时，所有合法 RAM 点上 rho 都为 1.75。

### N：辅助资源不敏感

在全部合法 CPU/RAM 点上 rho=1。
CN 中 DeepSpeech2 和 BERT 都使用 N；CM 中 BERT 仍使用 N。

N 仍必须遵守合法最小 CPU/RAM 配额和节点容量，不代表可以给零 CPU/零内存。

### M：RAM 敏感、CPU 平坦

仅在 CM 中用于 DeepSpeech2。

对每个既有 RAM 采样点 m，计算：
c_equiv = 3*m/62.5，
再在 C 的 CPU 曲线上线性插值并沿 CPU 轴重复。

现有 RAM 采样点的结果：
[0.37, 1, 1.75, 2.4, 2.4]。

该公式定义采样点；采样点之间继续由原插值器处理。
不额外添加 RAM 折点，不更换插值器，不扩大搜索网格。

### 其他要求

- CN 与 CM 使用相同轴、合法下限和 reference=1。
- 两者的 CIFAR/BERT 画像完全相同；只修改 DS 的 RAM 响应。
- ImageNet 原画像完整保留，但本轮两条输入没有 ImageNet，不能据此讨论其结果。
- 替换后的画像标注 profile_kind=synthetic_sensitivity，记录来源、推导公式和哈希。
- 这是受控敏感度模型，不宣称实际 DS/CIFAR 的 CPU/RAM 测量曲线就是新表。
- 不把 CIFAR 作业换成 BERT，也不通过改变 GPU 请求或训练长度制造配对。

这两份画像在比例点 (3,62.5) 上，对实际出现的全部应用均为 1。
因此 CN 与 CM 的 SIA-P 应具有一致的逐作业执行轨迹与最终结果。
该控制检查是本轮必须通过的检查之一。

原画像→CN 同时改变了多项辅助响应，属于总体敏感度结构对照；
CN→CM 才是仅改变 DS 的 RAM 响应的严格配对。

## 七、验证机会存在，并区分“有机会”与“算法找到机会”

正式实验前完成以下有限验证，不做参数搜索：

1. 原有测试通过，默认路径行为保留。
2. 通过少量作业/少量轮次的集成测试，确认自定义 CPU 容量和响应表同时进入 runner 与独立 audit。
3. 两条新 CSV 的非 time 字段、任务集合和顺序与原数据相同。
4. CPU2/CPU6 只修改 cpu 字段；GPU/RAM/节点数不变。
5. 所有比例配额在画像合法域内，避免 CPU/GPU<1 或 RAM/GPU<20.83。
6. 保留 rtx 校准设备、既有四应用、每类最多两节点及同型 4/8 GPU 结构。
7. 检查全部画像倍率为正、单调不减，并在指定比例点得到本提示词列出的倍率。
8. CN/CM 在比例点完全一致，且唯一表格差异来自 DS 的 RAM 响应。

可用以下静态例子说明“为什么增加了机会”：

一台 8 GPU、24 CPU、500 GB 节点，含：
- 4 GPU 的 C 类任务；
- 2 GPU 的 M 类任务；
- 2 GPU 的 N 类任务。

合法配额为：
C：20 CPU / 83.32 GB，rho=1.53；
M：2 CPU / 375 GB，rho=2.4；
N：2 CPU / 41.66 GB，rho=1。
总计 24 CPU / 499.98 GB，三任务均不低于比例性能。

这只是可行性和机制示例，不要求完整动态实验保持该 GPU 计划，不把该例的倍率当作最终 JCT 收益。

### 已知 RAM 候选粒度问题：必须诊断，不能混入算法修改

在同一节点上放 4 GPU C + 4 GPU M：

- 当前有限候选器可能给 C：20 CPU / 83.32 GB，rho=1.53；
  M：4 CPU / 250 GB，rho=1，并留下 166.68 GB。
- 合法连续配额 M=416.68 GB 可使其 rho 约为 1.50004，其他任务不变。
- 但在没有兼容的当前中间配额点时，416.68 可能不在本轮有限候选池中；原比例边界是 250，下一画像点是 500。

请静态复核并记录这个事实。它说明物理可行机会可能被 RAM 候选粒度遗漏，不能因此直接宣称实际主轨迹已存在同样瓶颈。

本轮保持 v2 算法不变：
- 不偷偷增加中间 RAM 点、改变候选生成、扩大搜索或重调 H。
- 正式日志结束后检查是否真实出现“有闲置 RAM、同节点增配可提速、却未被分配”的事件。
- 如出现，给出原始轮次与合法配额证书，并列为下一版算法改进依据。
- 该诊断不阻止按当前冻结设计完成 18 格，也不要求每个机会都被利用。

## 八、机会统计与正确收益口径

除完成数、mean/P50/P95/P99 JCT、makespan、waiting/training/recovery 外，至少统计：

### 8.1 相对本场景比例配额的增益

对每个实际训练段，根据该任务 GPU 数和所在节点计算：
rho_prop = rho(该节点的比例 CPU/RAM)；
relative_gain_ratio = rho_actual / rho_prop。

报告：
- 训练时间加权 rho；
- 训练时间加权 rho/rho_prop；
- rho>rho_prop 的实际训练时间占比；
- GPU/CPU/RAM 按类型及节点的分配占比，明确包含恢复占用，不能称为硬件忙碌利用率。

不能将 CPU6 下的 rho>1 直接解释为超过同场景比例分配；CPU2 下 rho=1 也可能已经明显超过比例点。

### 8.2 CPU/RAM 条件贡献

分别计算：
CPU 条件差 = rho(c_actual,m_actual) - rho(c_prop,m_actual)；
RAM 条件差 = rho(c_actual,m_actual) - rho(c_actual,m_prop)。

报告其训练时间加权均值和正增益训练占比。
两者在存在耦合时不能直接相加为总收益，也不能直接换算成跨运行的 JCT 因果贡献。

### 8.3 机会从哪里被限制

按实际训练时间和非空轮次统计，避免只数任务个数：

- C、N、M 及实际应用的训练时间/GPU 时间占比。
- 不同敏感度任务是否同时被 Sia 选中。
- 是否分到同一 GPU 类型。
- GPU 数之和是否允许同节点放置。
- 是否被恢复锁限制。
- F 是否已经将互补任务放在一起。
- 同类型其他节点的 GPU 容量是否阻止迁移。
- F/K/R 可行次数、选择次数、Phi 相对 F 的分布。
- R 的未扣恢复 sum-rho 是否高于 F，R 的优势是否仅来自较少恢复。
- 实际迁移次数、纯节点迁移次数、aux-only 更新和恢复时间。
- 固定其他任务与位置不变，使用本节点现有空闲 CPU/RAM 是否还能产生合法正收益。每个证书独立成立，不把多个任务同时占用同一份空闲资源的收益相加。

这些指标用于区分：
“没有机会”“有机会但受 GPU/锁约束”“配额候选漏点”“F 已经充分利用”“R 没找到更好的布局”“迁移成本抵消收益”。

## 九、运行与冻结顺序

A. 核查 v2 原成果及代码版本。
B. 完成仅与场景输入有关的最小接口适配。
C. 生成六场景文件，完成上面的短验证。

F. 独立从原始事件复算，检查 CN/CM SIA-P 控制。
G. 形成报告与复现交付，结束本轮。

冻结清单至少含：
- 基础 v2 提交、当前运行源码提交或可还原差异/源代码归档；
- 原算法保护哈希，证明本轮调度策略未改；
- 原输入保护哈希；
- 六场景的输入/集群/响应表哈希及生成器版本；
- Python/锁定依赖/求解器、种子 0、数值线程数 1；
- 60 秒周期、H=180、原恢复费用、原性能参考点；
- 每格输出目录、固定顺序、总预算、失败和停止规则。

沿用原 v2 的执行假设：
控制器墙钟耗时单独报告，不扣入模拟 JCT；真实启动/迁移恢复计入 JCT。
三种方法使用完全相同的场景输入、共同成本和节点稳定处理；Fixed 与 CAPRA 共享 v2 配额分配器。

如果发现输入传递或审计的真正 bug，保留失败运行，停止后续正式格，修复后形成新的冻结版本；不把不同版本结果拼成完整矩阵。
如果是当前算法固有的机会遗漏或性能退化，记录证据并完成既定实验，不现场修改算法。

## 十、原始日志审计与控制检查

对每格独立复算：

- 全部 80 作业的到达、完成时间和 JCT；

- GPU/CPU/RAM 逐节点容量；

完整决策开销使用与原报告一致的非空决策轮次，报告 median/P95/max；

## 十一、预算与停止条件

- 本轮只安排六场景 × 三方法，18 格。
- 不扫到达倍率、CPU 数、画像强度或 H；不因没赢而增加场景或随机种子。
- 单格模拟器 wall_limit=900 秒，所属进程外部上限 960 秒，max_rounds=6000。
- 保留无进展、连续过慢决策和用户 STOP_REQUEST 等止损。
- 累计实验预算 120 分钟，含准备性运行、失败/允许的环境重试，以及正式矩阵的核验、写盘和进程清理时间。
- 使用一个单调时钟总截止时间，不能每次重试重新获得完整预算；给超时清理留出余量。
- 在实际平台上确认能够停止本轮拥有的程序和求解器后代；不能只把父进程退出当作整个进程树结束，也不能按 python 名称批量杀其他进程。
- 只对明确的环境/执行故障做有限重试，并写入新目录和预算账本。
- 正确完成但提升小、Fixed 获胜或尾部退化，都不是重跑理由。
- 审计失败时停止后续正式格；达到预算时保留已完成、失败和未运行格。
- 未完成格不报告全体平均 JCT/P95/P99，不能用完成子集代替。
- 定期报告正在执行的场景/方法、完成数、墙钟耗时和有无错误。

预算是停止上限，不是承诺全部开发、调试和实验两小时内完成。
