## 二、已发现的问题：把这些作为回归目标

以下为此前审查的事实或反例，先结合实际版本核实，不能当作要求算法必须达到的实验结果：

- 原分配器主要在 preferred 和 proportional 两种配额间切换，可能留着空闲 CPU，却不给仍有边际收益的任务增配。
- peer_proportional 可能把原本只需 1 CPU 的 BERT 抬回 3 CPU，没有性能收益，还占用可让其他任务加速的 CPU。
- 按 GPU 数量排序、按剩余 GPU best-fit 放置，并不直接评价 CPU/RAM 性能互补。
- 旧分配接口没有充分利用上一轮真实执行位置；相同硬件节点的编号选择可能引起无收益迁移。
- 现有上游 Sia 对 CIFAR 的重启预测值为 30 秒，而当前应用执行恢复值为 50 秒，需要核实并统一来源。
- 同状态重放中，原主轨迹上的 free 方案并没有表现出比 Fixed 更低的即时 rho；不能把构造出的装箱反例冒充原轨迹退化的直接原因。
- 原主负载中辅助资源收益机会有限。当前响应表在比例 RAM 以上大体饱和，不能凭这两条负载宣称 RAM 优化效果已经充分验证。

原冻结结果仅供核对，不作为新版主表的同版本基线：
saturn-2-supported80：SIA-P 1141.6625 秒，CAPRA-Fixed 1048.4250 秒，CAPRA 1125.6125 秒。
saturn-6-supported80：SIA-P 1125.4625 秒，CAPRA-Fixed 1144.8375 秒，CAPRA 1109.7000 秒。
以上均为平均 JCT。

## 三、第一项修改：三种方法共同使用节点稳定与成本语义

### 3.1 显式传递真实执行状态

第二阶段必须接收上一轮实际 current allocations、当前 GPU plan、恢复 locks、各锁剩余恢复时间和应用信息。

- current 必须来自真实提交后的状态，不能用上一轮 Sia 的参考放置代替。
- 只有正在恢复的 locks 是硬约束：物理节点、GPU 配置、CPU、RAM 和已有恢复状态均不得改变。
- 未锁定任务的旧位置是软偏好，不得全部锁死；否则无法纠正资源互补性差的共置。
- 未锁定的旧超比例配额也不是永久承诺，可以在整体方案中调整，但必须满足本任务的比例性能保底。

### 3.2 共同消除等价节点编号造成的无收益迁移

实现一个共享、纯函数式的节点身份稳定步骤，SIA-P、CAPRA-Fixed、CAPRA 全部使用。

- 只能在 GPU 类型、GPU 数量、CPU 容量、RAM 容量及其他影响模型的属性完全相同的节点之间做映射。
- 当前每种 GPU 类型有两个相同节点，只需比较“不交换”和“整体交换”两种映射；不要为一般多节点情况引入阶乘枚举。
- 映射必须保持候选内的同机任务组合、每个任务的 GPU 配置、CPU/RAM 配额和 rho 不变。
- 锁定任务必须留在原物理节点。存在冲突的映射直接不可用。
- 用统一成本函数比较整个映射引起的恢复代价，选择代价较低者；不能仅以迁移任务个数或保留 GPU 数代替真实成本。
- 平局采用冻结的确定性规则。对相同 current/locks，稳定映射须具有幂等性，重复应用不能使两个节点来回翻转。
- 这是在提交前选择真实物理节点，不是事后改日志中的节点编号；真正发生的迁移继续收费。

先对共同 Sia 参考方案执行该步骤，产生稳定的参考节点映射。对 F/K/R 完整候选也使用同一规则。F 与 Fixed 必须共用同一调用路径；参考映射稳定后，再稳定 F 不得改变其物理节点。Fixed 的节点约束和审计以这个共同参考为准。

日志分别保存：原始 Sia 节点方案、既有锁可执行性修复、共同稳定后的参考节点方案、候选映射和最终执行方案。不要混写成一个 original_plan。

### 3.3 单一成本来源与预测/执行一致

建立可复用的纯状态转换/成本函数，供节点映射、候选评分和执行器使用；让 Sia 阶段的相应恢复成本参数也读取同一应用成本来源。

- 不要把 CIFAR 30 秒和 50 秒两个常数分别保留在预测与执行路径中。
- 成本由应用与目标设备等真实执行模型所需信息决定，不按具体任务名字、负载或实验结果特殊处理。
- 正在恢复的锁使用已有剩余恢复时间，不重新收取完整恢复成本。
- 新启动、恢复运行、GPU 类型/数量/物理节点变化，按现有执行语义计算一次相应恢复成本；多个属性同时变化不能重复叠加。
- 仅 CPU/RAM 配额改变继续采用当前模型的零 GPU 恢复成本假设，三种方法一致。
- Sia 已决定的 GPU 重配置成本必须对所有候选同样计算，不得只记给自由放置候选。
- 区分“新增恢复成本”“已有恢复剩余”“本窗口实际消耗的恢复时间”。例如新增 120 秒恢复，不代表本轮 60 秒内实际消耗了 120 秒。
- 候选试算不能改变 live Job、进度、batch、恢复倒计时或在线画像。选定最终方案后只提交一次。
- 预测的新成本与实际 commit 产生的新成本逐事件核验；不要求固定窗口预测进度等于后续动态调度的实际进度。

如果需要上游补丁，保持最小改动并记录补丁和来源，不把临时诊断 monkeypatch 直接当正式实现。

## 四、第二项修改：Fixed 和 CAPRA 共用新的节点内配额分配器

输入为完整的“任务到节点”布局；输出为完整、可验证的 CPU/RAM 配额。Fixed 与自由放置必须调用同一个实现、同一响应函数和同一参数。

### 4.1 先建立完整保底，再分剩余资源

对节点上的完整任务集合：

1. 精确保留 locks 的实际配额。
2. 给所有其他任务预留按 GPU 份额计算的比例配额。
3. 先验证整个布局的 GPU、CPU、RAM、任务集合和锁约束。
4. 再无损回收冗余资源，并将剩余资源分给有收益的任务。

构造布局期间可在副本上估计节点收益，但不能把先到任务的峰值配额提前写进最终预留，挤掉后续任务的保底。

每个非锁任务至少满足：
rho(final) >= rho(本候选节点上的比例配额) - epsilon。

锁维持精确状态，不因“可回收”而改动。F 的保底若不可行，视为正确性失败，不能通过删任务完成。

### 4.2 冻结有限的 CPU/RAM 配额对

CPU/RAM 在 Allocation 中均表示任务总量。画像若按每 GPU 给出，只转换一次；不要对已有总配额再乘 GPU 数。

为每个任务/节点建立有限候选配额对，至少包括：

- 画像中的合法 CPU/RAM 组合。
- 精确比例配额。
- GPU 配置兼容时的当前配额点，重新计算 rho。
- 以“任务总 CPU 每次 1 核”为粒度的合法中间 CPU 点，配合有限 RAM 点。
- 从本次完整比例基准和精确锁配额计算出的有限边界点：对每个任务各计算一次“节点 CPU/RAM 容量减去其他任务基准占用”的可用容量边界，不枚举其他任务配额组合来生成边界。

RAM 点使用画像轴、比例点、合法当前点及上述容量边界；本轮不引入任意精细连续 RAM 搜索。候选点数及其生成耗时计入日志和完整开销。

候选集合在一次分配求解前生成、去重并冻结；任何边界点也在此时产生。禁止在升级循环中不断追加浮点候选。不得利用画像边界 clamp，把 CPU/RAM 降到合法最小画像范围以下还声称 rho 不变。

必须支持 4 GPU 任务总 CPU 从 12 增到 18 这种中间点，不能只允许“画像 CPU 轴 × GPU 数”。

### 4.3 成对无损回收

只能从同一个合法配额对 (c',m') 证明回收成立：

rho(c',m') >= rho(c,m) - epsilon；
c' <= c；
m' <= m。

不能分别求最小 CPU、最小 RAM 再拼成一个从未验证的组合。

对可行的回收点使用冻结的确定性选择，例如资源归一化占用最小，其后固定字典序。不要把 BERT 从 1 CPU 无理由重置到 3 CPU。

在完整布局上允许保留兼容、整体可行的当前配额作为有限初始解/候选。每次节点内分配调用至多处理两个完整初始向量：
- 该节点全体未锁任务的比例配额向量，锁保持精确配额；这个保底解始终存在。
- 该节点全部兼容任务采用当前配额、其余任务采用比例配额的一个向量；整个向量不合法则丢弃，不搜索哪些任务保留旧配额的子集。
- 两个初始解都用相同有限回收和升级过程，按该节点总 rho 选择，平局按资源占用与固定顺序决定。
- 每节点选出唯一结果后直接拼接为完整布局，不枚举逐任务或跨节点的初始解组合，也不产生额外布局。

### 4.4 用有限的成对增量升级分配空闲资源

对每个未锁任务的合法候选 (c',m') 计算增益，并检查替换旧配额后的整体节点容量。更新计入 new-old，避免保底与新配额重复预留。

优先级采用：

priority =
[rho(c',m') - rho(c,m)]
/
[max(0,c'-c)/node_cpu + max(0,m'-m)/node_ram]。

- 只接受超过固定容差的正收益升级。
- 零分母、无资源增加的支配改善在回收/支配步骤处理，不能出现除零。
- 必须同时考虑 CPU 和 RAM 联合增加的候选，不能因为单独增加其中一种没收益，就漏掉联合升级。
- 固定所有平局规则。
- 每个初始解先进行一次确定性回收，之后只做严格 rho 增长的有限升级。
- 候选数为 K_j 时，每个任务最多升级 K_j-1 次；显式记录/限制总循环次数。缓存重复 rho 和节点试算，避免开销膨胀。
- 总 rho 贪心只是配额启发式，不宣称求得全局最优或 JCT 最优。

没有收益的空闲资源可以保留为空闲。不要为了报告“利用率更高”而盲目分完所有 CPU/RAM。

## 五、第三项修改：只构造 F、K、R 三个完整布局

所有候选保持本轮同一获选任务集合、GPU 类型、数量、单节点 shape 和 batch 快照。

### F：共享 Fixed 候选

共同稳定后的 Sia 参考放置，调用上述共享节点配额分配器。

对同一状态、同一 GPU plan、同一锁和配置：
CAPRA 内部 F 必须与新版 CAPRA-Fixed 的共享函数输出完全一致。

F 是完整可行 incumbent，始终保留。K/R 失败时返回已求出的 F，不重新退回更差的全比例方案。F 不可行是故障，不是可忽略候选失败。

### K：优先保留当前真实位置

- 对 GPU 类型和数量与本轮计划兼容的未锁任务，优先留在当前物理节点。
- 再安排新启动或 GPU 配置改变的任务。
- 不允许为了保留位置而保留旧 GPU 配置。
- 用比例资源预留完成布局，之后调用共享配额分配器。
- 只能构造一个确定性的完整 K；如果无法放下全体任务，记录失败原因并丢弃。
- 不把旧位置变成 R 的硬约束，不对 K 做递归挪动/回溯修补。

### R：资源感知的确定性重排

只对非锁任务重排。首先处理占满整台节点或只有一个可行节点的任务，避免碎片；其后按辅助资源压力排序。

设任务 preferred 配额为同一个可行配额对 (c*,m*)，任务 GPU 为 g，节点容量为 (G,C,M)，可用：

s_j = max(0, c*/C - g/G, m*/M - g/G)。

不能把分别最小化得到的 CPU/RAM 拼成 preferred。排序和并列规则先写入配置/设计，再冻结。

评估放到某个节点时：

- 对该节点的全部已放任务加新任务调用共享配额试算。
- 比较加入前后整个节点的总 rho 增量，包含对所有 peer 的影响。
- 不能只比较新任务是否能拿到 preferred，也不能只按剩余 GPU best-fit。
- 同收益优先当前物理节点/较小恢复代价，其后固定节点顺序。
- 正式构造状态仅保留 locks 和比例预留；试算得到的额外配额不提前永久占用。
- 每一步检查 GPU、CPU/RAM 保底与锁；最后必须完整验证后再增配。

当前每种 GPU 类型两个节点，增加轻量的剩余 GPU 容量可行性检查：
- 对未放任务的 GPU 数做有界子集和/动态规划，检查能否放入两个剩余容量。
- 有任务只能去特定节点时纳入该约束。
- 例如两台 8 GPU 节点与任务 8+2+2，不能先把两个小任务分散，导致 8 GPU 任务无处可放。
- 这只是 GPU 装箱检查；CPU/RAM 与 locks 仍须单独验证。
- 不推广成新的全局资源 MIP。

任一候选失败，记录原因并丢弃整个候选，不能返回部分成功。外层最多 F/K/R 三个布局；不从获胜布局继续派生新布局，不进行连续交换搜索。

## 六、第四项修改：按恢复成本后的固定窗口总收益选择

本轮固定调度间隔 60 秒；评分窗口预先固定 H=180 秒。

H 仅用于评价，不把调度间隔改成 180 秒，不强制 Sia 持续同一 GPU 配置三轮，不额外扣除 H 秒模拟时间。本轮不扫描 H、不依据主实验调 H。

对完整候选 A：

Phi_H(A) = sum_j rho_j(A) * max(0, 1 - d_j(A)/H)。

其中：
- 锁内任务 d_j 为已有剩余恢复时间。
- 非锁任务按统一执行模型，预测本次启动/恢复/重配置/换节点后的恢复时间；只计一次。
- 保持相同 GPU 配置和节点、仅改变 CPU/RAM 时 d_j=0。
- 对同一任务，各候选 GPU 配置和 batch 相同，rho 表示相对于该任务比例参考速度的倍率；不直接把不同模型的样本数或原始 goodput 相加。

对共同节点身份稳定后的所有可行完整候选计算 Phi_H，选择最大者。平局依次选：
1. 总恢复代价更低；
2. 真实 GPU/物理节点变更更少；
3. 固定候选次序 F、K、R。
明确浮点容差，并验证 Phi_H(selected) + epsilon >= Phi_H(F)。

注意：
- 评价全体任务，不只看被移动任务或新任务。
- 不增加“每个任务窗口进度都不得降低”的迁移门槛；这会禁止移动低资源需求任务以帮助其他任务的必要重排。
- 真实迁移成本照常收取，不能通过关闭成本保证迁移通过。
- H=180 是本轮冻结的启发式，不是已证明最优的窗口。
- 允许近完成任务被固定窗口估计不准；报告这个局限，本轮不另造 ETA 预测器补救。
- F 存在只能保证同状态、同模型下所选方案的 Phi 不低于 F，不能保证动态完整运行中的每个任务 JCT、平均 JCT、P95/P99 都不退化。

解释性检验：
rho 从 1 提高到 1.75，恢复成本 50 秒；
H=180 时，保留方案等效进度 180，迁移方案为 (180-50)*1.75=227.5；
H=60 时迁移方案只有 17.5，显示一轮窗口可能过于保守。
这个检验用于验证公式，不作为改造主负载或调参的理由。

## 七、验证：覆盖实际风险，不堆砌无意义测试

保留原有测试。新增少量直接覆盖以下机制的测试/可复现 fixture，可合并相关情况：

1. 等价节点：只因编号不同的同型布局应避免无收益迁移；映射不改变共置、GPU、配额和 rho；锁精确保留，重复稳定处理保持幂等。不能据此禁止所有单任务 rho 不变的迁移，某些迁移可能帮助同伴。
2. CPU 中间点：
   - 8 GPU/24 CPU 节点，CIFAR 2 GPU/18 CPU 与 CIFAR 1 GPU/3 CPU，共用 21 CPU；后者可以用剩余 3 CPU 达到总 CPU=6，rho 从 1 到 1.75。

3. BERT 回收：已有轨迹中两项 1 GPU BERT 各占 3 CPU 且 rho=1 的节点，验证可将其各降为 1 CPU，给同节点 CIFAR 增配；不能移动锁、降低保底或虚增容量。

5. 联合升级反例：rho(c,m)=min(c,m)，从 (1,1) 到 (2,2) 的收益不能因两个单资源步骤均无收益而漏掉。测试画像作为明确 fixture，不替换主实验响应表。

7. 8+2+2 GPU 碎片防护：存在完整方案时不能因先放小任务留下不可放的整节点任务。
8. 纯候选与一次提交：F/K/R 试算不污染 live state；start、resume、同型换节点、类型/卡数改变、锁剩余恢复和 aux-only 的成本预测与提交一致，恢复不重复收费。
