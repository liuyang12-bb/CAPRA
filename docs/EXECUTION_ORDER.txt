# CAPRA 独立项目执行单

项目名称：CAPRA
英文展开：Configuration-Aware Placement and Resource Allocation
中文说明：配置感知的任务放置与资源分配
研究范围：Sia 每轮选择 GPU 配置，第二阶段利用 Synergy 的方法协调物理节点放置与 CPU／主机内存配额。

## 三、实现清楚的两阶段契约

### 1. 第一阶段由 Sia 决定 GPU 配置

每轮获得：
- 本轮运行作业集合；
- 每个作业的 GPU 类型、GPU 数量、节点数；
- 与该配置对应的合法每节点 GPU 分布形状；
- 当前实际状态、上一轮节点分配、checkpoint/恢复锁。

Sia MIP 没有独立的 Batch Size 输出变量。沿用 Sia 对已选 GPU 配置的批大小选择规则，取得当前的 atomic_bsz、accum_steps 等评估快照。第二阶段不新增 batch 搜索；训练中若按原规则继续更新 batch，应记录变化并保持画像使用假设明确。

接口可采用简单的 GpuPlan/JobGpuPlan 数据结构。默认流程保持获选集合与配置，不在第二阶段增加第二套准入策略。

### 2. 第二阶段决定物理节点和辅助资源

输入固定 GPU 计划、节点容量及画像。
输出：
- 每个作业的具体节点和逐节点 GPU 数；
- CPU 核配额、主机 RAM 配额；
- 与最终资源配置匹配的性能响应；
- 回退、迁移及可行性记录。

复用 Synergy-TUNE 的思想：
- 依据画像获得辅助需求；
- 结合 GPU、CPU、RAM 容量选择节点；
- 必要时将当前作业或相关已放置作业的辅助配额回退到比例份额；
- 保留其相对比例分配的预测性能保护。

先核对官方实现，再进行最小适配。若某个细节根据论文重实现，明确标为重实现；若排序、节点选择或回退范围经过适配，写明差异。固定节点编号顺序不等同于动态 best-fit，不能混写。

不要求新写一个 CPU/RAM MIP，不要求增加完成时间打分或局部搜索来“证明创新”。

### 3. 完整集合、资源与提交一致

正常返回必须满足：
- 返回作业集合与最终接受的 Sia GPU 计划相同；
- GPU 类型、数量、节点数和 shape 满足固定计划；
- 每个节点的 GPU、CPU、RAM 不超容量；
- 作业唯一放置，资源元数据和实际执行节点一致；
- 正在恢复的作业保持必须锁定的位置和配额；
- 候选计算不修改正在运行的状态，最后统一提交。

Synergy 原算法或适配代码如果最终放不下某个任务，不能默默删除它后报告成功。使用经验证的完整可行回退；若精确锁、GPU 碎片或最低辅助需求使计划本身不可执行，应明确记录。

如确需可行性修复，在三种比较方法的共同上层处理，保留 Sia 的目标，并记录修复前后的计划及原因。不能一方面修改了第一次 GPU 输出，另一方面声称完全保持了第一次输出。

### 4. 执行模型

以 Sia 的训练推进逻辑为基础，将辅助响应倍率作用于有效训练进度一次。CPU/RAM 资源不跨节点借用，主机 RAM 与 GPU 显存区分。

明确同类型、同 GPU 数／同 shape 但物理节点身份改变的迁移。不能仅比较每节点 GPU 数而漏掉节点搬迁，恢复代价要在实际推进中扣除。仅调整辅助配额沿用统一的执行假设，不凭空触发 GPU 迁移。

等待、checkpoint 和恢复时间不乘辅助速度倍率。逐作业输出可复核的状态与进度，必要的资源容量检查放在统一执行层。

## 四、第一版支持域和性能模型

先支持：
- 异构 GPU 集群；
- 每种 GPU 类型可有多个物理节点；
- 每个作业本阶段只占一个节点；
- 数据并行训练；
- GPU 配置随调度轮次调整，批大小行为沿用 Sia。

单作业跨节点和流水线暂列后续范围。本阶段所有方法使用相同 GPU 配置可行域。

主比较默认沿用已知每节点规格：
- aws：每节点 4 GPU、12 CPU、250 GB RAM；
- dgx-ext：每节点 8 GPU、24 CPU、500 GB RAM；
- rtx：每节点 8 GPU、24 CPU、500 GB RAM；
- 每种类型 2 台，共 40 GPU。

如选择其他现成拓扑，必须在新结果出现前登记并冻结，三种方法完全共用。旧项目不同拓扑的绝对 JCT 不直接加入新主表。

使用统一、可解释的画像映射和归一化响应模型。允许合理、内部一致的合成数据；明确哪些来自上游画像、哪些是映射或模型假设。不要为了新项目强制要求采集完整实机数据，也不要声称单张旧画像已经实测覆盖任意 GPU 数和 batch。

若复制旧项目中适用的输入文件，将其放进 CAPRA/data，并记录来源、哈希、转换规则。调度运行不得再次读取旧目录。

## 五、新项目内部只实现三个比较方法

1. SIA-P
   原 Sia GPU 配置和原节点放置，CPU/RAM 按 GPU 比例分配。

2. CAPRA-Fixed
   保留原 Sia 本轮节点放置，使用与完整 CAPRA 相同的画像、辅助配额调整、性能保护和回退规则；仅限制物理节点选择。

3. CAPRA
   原 Sia GPU 配置，允许第二阶段选择合法物理节点，使用同一套辅助配额调整。

CAPRA 与 CAPRA-Fixed 共用实现，最好通过一个明确的 placement mode 限制候选节点，避免写成两套不相关的辅助算法。

CAPRA-Fixed 是新项目中的控制版本，不是旧 SIA-AUX。不要把旧 SIA-AUX 的 ETA MILP 导入 CAPRA，也不要把两者的数据混为一谈。

固定 GPU 计划是单个决策内部的接口。完整运行中，各方法的进度、完成事件和队列会分化，后续 Sia 决策可以不同；不能强行要求完整 trace 的所有 GPU 决策序列一致。

## 六、先完成小验证

只做直接对应真实风险的必要检查，并复用上游相关测试。

A. 两节点四作业的资源互补例
固定同一份 GPU 计划：两台同类型节点，各 4 GPU／12 CPU／250 GB RAM；四个作业各 2 GPU、1 个节点，当前 global batch=128，剩余工作量各 600 个归一化进度单位。
构造响应（C、M 为每任务总 CPU 和 RAM）：
- A、B：r=10*min(C/8, M/50, 1)。
- C、D：r=10*min(C/4, M/200, 1)。
初始 A/B 同节点，C/D 同节点。比例配额各 6 CPU／125 GB。
比较 CAPRA-Fixed 与 CAPRA 的实际放置和配额。合法互补方案为每节点一个 CPU 敏感作业和一个 RAM 敏感作业，配额分别 8 CPU／50 GB 和 4 CPU／200 GB。
这是第二阶段机制输入，不伪装成原 Sia 必然会选择的配置或实测数据。检查每节点资源、真实执行速度和迁移计费。若实际贪心顺序未找到该方案，记录具体行为，不靠更换数据或增加搜索掩盖。

B. neutral 检查
辅助倍率设为 1，验证没有额外进度收益；恢复、等待和迁移时间不被倍率缩放。
只有在配置、部署轨迹和代价相同的条件下才要求进度或 JCT 一致。不同放置产生的迁移差异如实记录。

C. 同类型节点迁移、checkpoint 锁及完整回退
检查节点身份变化且 shape 不变的迁移仍扣时；锁定作业不被改动；部分返回不会提交；回退结果保留完整作业集合并满足容量。

D. 独立运行验证
从 CAPRA 的环境和入口启动，不通过旧目录导入模块或读取数据。检查配置路径、导入来源、输出路径和环境归属，无须实际移动或修改旧项目来测试。

小验证完成即汇报目录、来源版本、真实命令和结果，然后进入限定主比较。正确性验收不要求每个方法在每个例子中都获胜。

## 七、限定主实验：两份负载 × 三方法 = 六格

在看到 CAPRA 主结果前写好 manifest：
- 两份既有、适用本阶段支持域的轨迹派生负载；
- 固定选择规则和文件哈希；
- 所有方法共用的拓扑、画像、归一化参数、种子；
- GPU 可行域、批大小规则、调度周期、迁移／恢复模型；
- 实际代码状态、来源版本、运行顺序、终止规则及输出目录；
- 调度耗时如何统计、是否计入模拟执行时间。

优先使用固定规则选择的每份 80 个受支持作业，保留原始到达和训练工作量；如上游已有合适的小负载可直接采用。不要根据哪个输入让 CAPRA 获胜来选择。受控到达的机制负载应标明为受控负载。

每份运行 SIA-P、CAPRA-Fixed、CAPRA。先完成第一份的三格并交付小表，再继续第二份预登记负载。不自动扩大到旧的大矩阵。

所有主结果由 CAPRA 独立运行产生。旧 MELD 和旧 SIA-AUX 不作为这轮必须重跑的对象；旧结果仅作为研究背景，不搬入主比较表。

每格记录：
- 作业总数、完成数和未完成原因；
- 全部完成时的平均 JCT、P95/P99、makespan；
- 逐作业等待、训练、恢复时间和 JCT；
- 节点 GPU／CPU／RAM 分配；
- 迁移、重配置、回退次数及原因；
- 完整决策耗时的中位数、P95、最大值及整格墙钟时间；
- 原始事件、配置、哈希及可复现命令。

从原始事件复算指标。未完成时不把完成子集均值当作整体平均 JCT。

完整调度耗时包括 GPU 求解、画像处理、放置、配额和准备阶段。若模拟模型不扣实际调度时间，清楚标记并单独报告开销；若计入，采用共同规则及本版实测或校准值，不继承旧算法的固定延迟常量。

正式运行前用短验证估计耗时，给出实际估计依据。运行中持续报告当前格、完成数和耗时，不无限开启后台实验。资源不足时记录具体原因，不能通过终止旧项目解决。
